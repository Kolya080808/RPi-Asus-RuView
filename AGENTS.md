# Постоянные инструкции для Codex в ruview-lab

Эти правила применяются ко всем задачам в этом репозитории. Инструкции пользователя в текущем чате имеют приоритет, если явно задают другой порядок действий.

## Контекст проекта

- Главная цель проекта — заменить обычную систему наблюдения системой наблюдения за обстановкой посредством Wi-Fi радиосигналов, используя роутеры и репитеры ASUS. Итоговый приоритет — отображать человека в виде трёхмерного скелета; первый практический результат должен как минимум определять положение движущегося объекта. Не своди цель проекта к сбору данных или лабораторному исследованию CSI: сбор, анализ и эксперименты — этапы создания и проверки конечной системы.
- В текущем подтверждённом стенде GT-AX11000 выступает источником CSI, Raspberry Pi Zero 2 W — сборщиком и хранилищем, а ПК используется для управления, анализа и визуализации. При проектировании следующих этапов связывай техническую работу с конечной задачей замены системы наблюдения.
- Не приравнивай наличие команды `csimon` к доказанной возможности получать CSI. Возможности каждого устройства, интерфейса и профиля прошивки подтверждай отдельно.
- Декодер относится только к наблюдавшемуся профилю GT-AX11000; сохраняй исходные записи для повторного декодирования. Не называй индикатор движения распознаванием позы, частей тела, дыхания или пульса без отдельной проверки.
- Текущая реализация — Python. Не начинай перенос на C++ по собственной инициативе. Будущий перенос рассматривай как отдельный этап после того, как пользователь сочтёт Python-реализацию достаточно проверенной.
- Важная цель проекта — обратимость экспериментов с конфигурациями и файлами устройств. Это не означает автоматический factory reset: откат должен удалять или восстанавливать только точно учтённые изменения.
- Перед удалёнными изменениями на роутерах, репитерах или Pi зафиксируй исходное состояние, перечисли точные файлы, процессы и настройки, добавь соответствующее действие и проверку в `scripts/rollback.py` и обнови `deployment.json`/`docs/ROLLBACK.md` по их назначению. Сначала проверь план отката; после применения проверь фактическое состояние. Не отключай неизвестный процесс, не перезаписывай неизвестные ключи и не восстанавливай устройство к заводским настройкам.

## Границы безопасности и разрешённые устройства

- Проект выполняется пользователем исключительно для личного стенда. Тестируй код и данные локально на этом ПК; эксплуатационная диагностика допустима только на Raspberry Pi Zero 2 W, ASUS GT-AX11000, RP-AX56 и RP-AX58, перечисленных для проекта. Любое новое устройство пользователь должен явно добавить.
- Наступательные проверки разрешены в пределах собственной домашней локальной сети и явно перечисленных устройств проекта: сканирование, проверка уязвимостей, проверка аутентификации и ограниченный fuzzing допустимы при согласованной цели и объёме. Запрещены DoS, перегрузка, разрушение данных и постоянные изменения без отдельного плана и разрешения. Соблюдай фиксацию исходного состояния и откат из правил выше; при вероятности сбоя или перезагрузки остановись до изменения.
- Публичные источники, внешние адреса и сервисы можно использовать для ресерча и других законных задач. Это само по себе не разрешает активное тестирование чужих систем: для него нужны явное полномочие и отдельная область проверки. Не подключай рабочие сети или аккаунты для тестирования этого проекта и не отправляй во внешние сервисы код проекта, пароли, записи или приватные результаты.
- Пользователь особенно бережёт безопасность личного и рабочего аккаунтов. Не создавай связанной с проектом активности вне разрешённого стенда и не загружай данные проекта в сторонние сервисы. Перед устройственными экспериментами соблюдай фиксацию состояния и откат из правил выше.

## Начало каждого нового чата

- Pi по умолчанию недоступна. Перед работой, требующей подключения, сообщи пользователю, что нужен доступ, и дождись подтверждения доступности. Пользователь включает Pi по запросу; постоянный адрес SSH — `192.168.50.100`, пользователь — `pi`. Используй существующий ключ `~/.ssh/ruview_pi_lab` и проверку хоста через `~/.ssh/ruview_known_hosts`; при необходимости пароль предоставляется пользователем приватно и не записывается в репозиторий. В чате 2026-10-04 пользователь подтвердил доступность Pi для обновления панели.

- В начале каждого нового чата один раз составь актуальное представление проекта: посмотри `git status`, полный список файлов и папок, README, инструкции `AGENTS.md`, конфигурацию и зависимости, документацию, тесты и исходники. Для крупных областей чтение можно вести по компонентам, но ни одну значимую часть проекта не пропускай.
- Цель начального обзора — понять, что это за проект, как устроены компоненты, что подтверждено, что является гипотезой, какие есть ограничения, опасные данные, текущие изменения и следующие шаги. Не нужно заново перечитывать весь проект перед каждым сообщением или шагом в том же чате.
- Бинарные файлы, архивы, ключи, записи и базы данных сначала идентифицируй по имени, типу, размеру и местам использования. Не печатай и не раскрывай секреты. Не загружай и не анализируй содержимое приватных записей/БД без необходимости для задачи. Если база важна, начни с безопасного read-only осмотра схемы и метаданных; не меняй данные.
- После обзора используй уже собранный контекст в этом чате и обновляй его при появлении значительных изменений. Не делай повторное полное сканирование без причины.

## Планирование и параллельная работа

- Перед изменениями определи затрагиваемые компоненты, данные, устройство и документацию; сформулируй критерии результата и риски отката.
- Для сложного ресерча, реализации или ревью можно привлечь агентов, если параллельная работа даст заметную пользу. Обычно достаточно 2–3, абсолютный максимум — 4. Не запускай агентов для простых задач и не трать лимиты на дублирование.
- Давай каждому агенту отдельную ограниченную область и конкретный результат. Учитывай лимиты и стоимость; при небольшом ожидаемом выигрыше работай самостоятельно.
- Агенты только исследуют и предлагают. Основной агент проверяет выводы, сводит результаты и сам вносит все изменения в этом репозитории.

## Проверка фактов и гипотез

- Разделяй в сообщениях и документации наблюдения, выводы, гипотезы, решения пользователя и внешние утверждения. Указывай источник, дату, стенд/условия и ограничения там, где это важно.
- Важный вывод или гипотезу по возможности подтверждай независимым способом, который не повторяет тот же расчёт или путь получения данных. Подходящие пары: анализ сырых данных и отдельный тест; измерение и геометрический/математический расчёт; повторный эксперимент и независимый инструмент; воспроизведение ошибки другим сценарием и проверка логов.
- Повторное мнение агента полезно для ревью, но само по себе не является независимым доказательством, если оно использует те же данные и рассуждения.
- Если независимая проверка невозможна, прямо пометь результат как предварительный, укажи, что именно не проверено, и предложи конкретный следующий эксперимент.
- Не усиливай формулировку результата сверх того, что позволяют данные. Сохраняй ограничения и неудачные/неоднозначные эксперименты.

## Реализация и обратимость

- Перед редактированием проверь `git status` и сохрани пользовательские незакоммиченные изменения. Работай в текущей ветке. Не создавай ветки автоматически.
- Делай небольшие, относящиеся к задаче изменения; придерживайся структуры и соглашений проекта. Не исправляй попутно несвязанные проблемы.
- Разрешено устанавливать зависимости, когда они нужны. Сначала проверь, нельзя ли обойтись уже установленными средствами; используй подходящую версию и обнови файл зависимостей и документацию. Не устанавливай пакеты на роутер/Pi или системные пакеты устройств без конкретной необходимости и плана отката.
- Считай потенциально необратимыми удаление/перезапись данных, миграции, очистку БД и истории, изменение конфигурации устройств, установку служб, автозапуск и прошивку. Перед таким действием определи точный объём, резервную копию/способ восстановления, проверку результата и влияние на действующие данные.
- Предпочитай сначала режим проверки, dry-run, копию или транзакцию. Не удаляй исходные записи и историю без отдельного решения пользователя. При неопределённости в состоянии устройства остановись до изменения и запроси конкретное решение.
- Локальные изменения кода должны оставаться обозримыми через diff. Не затирай и не откатывай изменения пользователя. Не запускай разрушительные Git-команды и принудительные операции с remote.

## Python, ошибки и логирование

- Для ошибок выбирай явную остановку с полезным сообщением и диагностикой, а не молчаливое восстановление или продолжение с потенциально ложными данными. Восстанавливайся только там, где поведение безопасно, ограничено и проверяемо; документируй такое поведение.
- Используй стандартный модуль `logging` вместо отладочных `print`. Для пользовательского CLI допустимы `print`/вывод через CLI, но диагностика должна быть отделена и иметь корректный уровень.
- Применяй уровни по смыслу: `DEBUG` для подробностей диагностики, `INFO` для этапов и штатных операций, `WARNING` для подозрительных, но обработанных состояний, `ERROR` для завершившейся ошибкой операции, `CRITICAL` для ситуации, требующей немедленной остановки/вмешательства.
- Логи должны помогать восстановить ход операции: указывай действие, компонент/устройство, идентификатор сессии или операции, существенные параметры, длительность/результат и контекст исключения. При обработке исключения сохраняй traceback (`logger.exception` или эквивалент), не скрывай исходную причину.
- Не логируй пароли, приватные ключи, токены, полные секретные конфигурации, чувствительные данные пользователей и содержимое записей без необходимости. Проверяй, что сообщения об ошибках и команды не раскрывают секреты.
- Для постоянно работающих или повторно запускаемых процессов учитывай размер, ротацию и срок хранения логов; не вводи чрезмерную детализацию на уровне INFO. Уточняй место хранения и способ просмотра логов в документации.
- Сохраняй полные диагностические логи и историю событий в течение нескольких недель, затем удаляй по документированной политике хранения. Применяй срок ко всем местам хранения логов, включая файлы захвата и записи логов в истории сессий; точное число недель должно быть отражено в документации после уточнения. Не удаляй исходные CSI-записи как побочный эффект очистки логов.
- Для новых подсистем придерживайся единого, понятного формата. Не добавляй сложный logging-фреймворк без необходимости. Если выбор ротации, срока хранения или формата влияет на историю/место на Pi, документируй решение и его последствия.

## Тесты и контроль качества

- После изменений запускай подходящий набор проверок проекта. Для функциональных изменений проверяй затронутые сценарии и регрессии; для изменений интерфейсов/данных — совместимость формата и ошибочные входы; для rollback — режим проверки и верификацию целевого состояния без непредусмотренного изменения устройств.
- Тесты выполняй локально на ПК или на перечисленной Raspberry Pi. Запуск теста на роутере или репитере не считается локальным: он возможен только как отдельно обоснованная штатная диагностика с заранее записанным состоянием и проверяемым откатом. Не направляй тесты на любые другие устройства или сети.
- Перед объявлением задачи готовой проверь работоспособность, ошибки кода и логики, граничные случаи, качество диагностики и очевидные ошибки документации/написания.
- Сначала используй уже принятый в проекте test runner и настройки. Если общего проверочного набора нет, выясни доступные команды из конфигурации и README, затем добавь только проверки, нужные задаче. Не вводи новый обязательный линтер/форматтер без причины; при добавлении инструмента зафиксируй его конфигурацию и команду.
- Не утверждай, что проверки пройдены, если они не запускались. Сообщай точную команду, результат и непроверенные области.

## Документация и передача контекста

- Документация — часть каждой задачи. По ходу работы фиксируй существенные новые факты, решения, неудачные попытки, изменения и их причины, результаты проверок, ограничения и следующие шаги.
- Обновляй существующий тематический документ, когда он есть. Для экспериментов поддерживай `docs/EXPERIMENTS.md`; для состояния, решений и передачи контекста — `docs/HANDOFF.md`; для очередности работ — `docs/NEXT-STEPS.md`; для устройств — `docs/HARDWARE.md`; для отката — `docs/ROLLBACK.md`. Не дублируй один и тот же текст в нескольких местах без необходимости.
- Если обнаружена новая существенная информация или изменилось состояние проекта, обнови соответствующую документацию в рамках той же задачи. Удаляй устаревшие утверждения или явно отмечай их как исторические; не оставляй противоречащие инструкции.
- Документируй назначение новых модулей, публичных интерфейсов, форматов данных, важных решений и эксплуатационных действий. Комментариями объясняй причины и ограничения, а не пересказывай очевидный код.
- Сохраняй точные условия эксперимента, источник/дату, число записей, ошибки и потери, метод анализа, независимую проверку и пределы выводов. Отрицательный результат тоже полезен и должен быть воспроизводимым.
- Ответы пользователю пиши по-русски и средней подробности. Документацию репозитория веди на английском, следуя существующему стилю проекта, если пользователь не попросил иначе.
- По умолчанию сохраняй объём ответа примерно как в обсуждении приоритета проверки CSI на репитерах: около 150–250 слов, с конкретным выводом, основаниями, ограничениями и следующим шагом. Это ориентир по объёму, а не требование одного абзаца: используй несколько абзацев или короткий список по смыслу. Объём может варьироваться в зависимости от сложности и масштаба работы; для короткого подтверждения не добавляй текст искусственно. Применяй этот формат во всех задачах, если пользователь явно не запросил другой.

## Git, авторство и внешние действия

- Никогда не изменяй Git identity. Если пользователь просит коммит или другое действие, требующее авторства, используй только уже настроенные `user.name` и `user.email`; если авторство не настроено или не соответствует пользователю, остановись и сообщи об этом. Не подставляй имя/email агента и не создавай фиктивное авторство.
- Не создавай коммиты, теги, pull request и не отправляй изменения в remote, если пользователь явно этого не попросил.
- Не прошивай устройства, не меняй настройки роутеров/репитеров, не включай постоянный сбор, автозапуск или сетевые сервисы без соответствующего запроса и документированного способа отката.
- В рамках явно поставленной задачи можно выполнять ограниченные обратимые действия на устройствах после проверки исходного состояния и способа отката. Отдельно согласовывай прошивку, factory reset, удаление истории/записей, постоянные настройки, автозапуск и действия с неясным воздействием. При любом новом удалённом изменении заранее фиксируй исходное состояние и проверяй rollback.
- Не публикуй наружу приватные данные, записи, адреса, ключи или результаты экспериментов. Не добавляй секреты в код, документацию, логи или Git.
- Переданные пользователем пароли устройств хранятся локально в `.secrets/local-credentials.json`; каталог `.secrets/` исключён из Git. Это приватный файл с паролями в открытом виде, а не часть документации или резервной копии репозитория. Читай только необходимые поля непосредственно для авторизации, не печатай содержимое и не передавай пароли в аргументах команд. Новые предоставленные пароли сохраняй там же, сохраняя существующие записи; не ищи и не извлекай другие секреты без необходимости. Доступ по SSH к RP-AX58 и RP-AX56 с предоставленными учётными данными успешно проверен 2026-10-05; эти два входа подтверждены. Не делай выводов об учётных данных других устройств без проверки. Не используй `git add -f` для этого каталога.

## Завершение задачи

- Кратко перечисли результат и зачем он нужен, укажи затронутые файлы/устройства, выполненные проверки и их результаты.
- Отдельно укажи важные выводы и степень их подтверждения, незавершённые вопросы и следующие шаги. Для изменений устройств сообщи, где записаны исходное состояние и процедура отката.
- Не называй задачу завершённой, если документация, проверка результата или требуемый способ восстановления ещё не сделаны.
